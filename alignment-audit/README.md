# 填写说明

先读这一份，够用了。判断标准那一页是 `PROTOCOL.md`，中途不确定时回去查。

## 你要做什么

包里有 1028 个条目。每个条目给你：一个自然语言问题、一个数据库、一条 SQL。

对每条回答一个问题：**这条 SQL 回答了这个问题吗。**

把判定填进 `RESPONSES_E1.csv`（或 `RESPONSES_E2.csv`，看你拿到的是哪一份）。

## 三步开始

**第一步，确认包是完整的。** 在包的根目录执行：

    python3 run.py --check

应该看到 1028 条条目、0 个缺失数据库、0 条跑不起来的 SQL。任何一项不对就别开始，找我要新的包。

**第二步，看第一条。** 直接执行：

    python3 run.py

它会显示下一条还没填的条目，并且**替你把那条 SQL 在正确的数据库上跑出来**，把结果表打给你看。
你不需要自己找数据库文件，也不需要自己开 sqlite。

**第三步，填。** 打开 `RESPONSES_E1.csv`，找到那个 `item_id`，在 `verdict` 列填四个词之一：

| 填这个 | 什么时候填 |
|---|---|
| `answers` | 这条 SQL 回答了这个问题 |
| `does_not_answer` | 没有回答：答错对象、算错聚合、漏了或加错条件、返回的不是问题问的 |
| `question_underspecified` | 问题本身没说清，这条 SQL 和另一种合理读法都忠于问题 |
| `cannot_judge` | 跑不起来、数据库缺东西、或者问题读不懂 |

`note` 列可以留空，想写就写一句。

然后再执行一次 `python3 run.py`，它会跳到下一条。如此循环。

## 好用的几条命令

    python3 run.py                     接着上次，显示下一条没填的
    python3 run.py AL0413              跳到指定条目
    python3 run.py AL0413 --limit 50   结果行太多时多显示几行
    python3 run.py --progress          已填多少、还剩多少、有没有填错词
    python3 run.py --schema world_1    看某个数据库有哪些表和列
    python3 run.py --db world_1 --sql "select count(*) from city"

最后一条是给你自己探数据用的。数据库是只读打开的，你怎么跑都改不坏。

## 三件容易出错的事

**一、必须真的跑，不能只读 SQL。** `run.py` 已经替你跑了，看结果再判断。只读 SQL 会漏掉一整类
问题：一个在这个库上永远返回空表的过滤条件、一个建在文本列上的数值排序、一个漏了 ON 的连接。
这些不跑出来看不见。

**二、`question_underspecified` 不是"我不确定"。** 它的意思是问题本身没有固定住答案，两种读法
都对。你只是拿不准的时候，再跑几个查询看看数据，别用它兜底。这一档和 `cannot_judge` 都不会被
计入正确率的分子或分母，占比会单独报告，所以如实用它们不会"浪费"条目，硬选一边反而让结果失真。

**三、别改 `item_id` 那一列，也别调整行的顺序。** 只动 `verdict` 和 `note`。用 Excel 打开的话，
存回来的时候要选 CSV UTF-8，不要存成 xlsx。

## 独立判断

- 每条独立判断，不要回头改前面的，不要为了让分布看起来合理而调整。
- **不要和另一位判读人讨论条目。** 分歧会交给第三人处理，那是设计的一部分，不是失败。
- 条目顺序是随机打乱的，相邻两条之间没有任何关系。
- 这些 SQL 由语言模型生成。除此之外关于它们你不需要知道任何事，也请不要推测正确的比例大概是
  多少、这批条目分成几类、研究想证明什么。这些推测会系统性地影响判断。
