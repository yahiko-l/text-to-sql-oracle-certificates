# 专家判读协议

## 你要做的事

`ITEMS.md` 里有 1028 个条目。每个条目给你三样东西：一个自然语言问题、一个数据库名、一条 SQL。

对每一条，回答一个问题：**这条 SQL 回答了这个问题吗。**

在 `RESPONSES.csv` 的 `verdict` 列填四个词之一。`note` 列可留空。

## 必须执行，不要只读

在指定的数据库上**把这条 SQL 跑出来**，看它返回什么，再下判断。

只读 SQL 会漏掉一整类问题：一个在这个库上永远返回空表的过滤条件、一个建在文本列上的数值排序、
一个漏掉 ON 的连接。这些只有跑一遍才看得见。数据库文件的位置见 `README.md`。

## 四种判定

| 判定 | 含义 |
|---|---|
| `answers` | 这条 SQL 回答了这个问题。允许写法不同、列顺序不同、多返回一个显然无害的列。 |
| `does_not_answer` | 这条 SQL 没有回答这个问题：答错了对象、算错了聚合、漏了或加错了条件、返回的东西不是问题问的。 |
| `question_underspecified` | 问题本身没有固定住这条 SQL 与另一种合理读法的差别，两种读法都忠于问题。**不要**用它来表示"我不确定"。 |
| `cannot_judge` | 你无法判断：SQL 跑不起来、数据库缺东西、或问题你读不懂。 |

`question_underspecified` 和 `cannot_judge` 不会被计入正确率的分子或分母，它们的占比单独报告。
所以遇到真正含混的条目请如实用它们，不要硬选一边。

## 独立判断

- 每一条独立判断，不要回头改前面的，不要为了让分布"看起来合理"而调整。
- 不要和另一位判读人讨论。分歧会由第三人处理，那是设计的一部分。
- 条目顺序是随机打乱的，相邻条目之间没有任何关系。

## 关于这批数据，你需要知道和不需要知道的

这些 SQL 由语言模型生成。除此之外，关于它们**你不需要知道任何事**，也请不要去推测：
不要推测正确的比例大概是多少、不要推测这批条目分成几类、不要推测研究想证明什么。
这些推测都会系统性地影响判断。

本协议**刻意不给出示例**。上一轮审计用研究本身产出的错误类型做示例，事后发现那等于提前告诉
判读人该找什么。这一轮不重复该做法。你要用的判断标准就是上面那张表。
